# Homework 2e: RAG

## Summary

For this assignment I built a chatbot that answers gospel questions using the talks from the October 2026 General Conference. No model was trained on a conference from earlier this month, so the chatbot looks up the right talks and pastes them into the prompt before answering. This is retrieval augmented generation, or RAG, and the way I think about it is as an open-book test. The model only reads what we hand it for that one question, so the answer can only be as good as the search.

I built it two ways. In the first, my code always searches with the user's question before calling the model (RAG as preprocessing). In the second, the model gets a search tool and decides what to search for (RAG as a tool). Both work, and the tool version found better talks on every question it searched for, at about the same price.

## 2. How the search works

The ingest step uses the class code's default settings. It splits each talk into chunks of at most 1,200 characters, breaking between paragraphs when it can, so the 38 talks became 257 chunks of two to four paragraphs each. Each chunk is embedded by OpenAI and stored with metadata about which talk it came from. When a question comes in, the chatbot searches those chunks but gives the model the whole talk each match came from. A small chunk makes a focused vector that can find a specific idea, which I learned the hard way with dilution in 2d, but the model needs the whole talk to answer well and to know who's speaking.

In 2d I compared every query against every vector. Chroma uses an index called HNSW instead, which links each vector to its closest neighbors and searches by hopping toward whichever neighbor is closer to the question. That's much faster, but it can stop at a spot that only looks like the closest one, which is why vector databases don't have 100% recall. With only 257 vectors the search is basically exact, so this only matters at a much bigger scale.

Before loading the talks, I put six sentences into a test collection and guessed what would happen first. I guessed Chroma's distance would be 2 − 2 × cosine, and so did Claude, but it was 1 − cosine because OpenAI's embedding function tells Chroma to use cosine distance. I also correctly guessed that a metadata filter doesn't check relevance. Chroma always returns the closest results it has, no matter how far away they are, just like my "airplane" search in 2d.

## 3. Testing the search on its own

I ran five questions through the class's query command before building anything. The betting question worked best: the talk says "gambling" and "wagers" instead of "bet," and the search still found it because it matches on meaning. The vaguer questions did worse. "How can I be saved?" matched "whosoever will save his life shall lose it," which uses a different meaning of "save," and short closing testimonies kept showing up because they don't have much other text diluting them. The betting search also returned the same talk five times, which would have wasted most of the prompt.

## 4. Building the chatbot

The chatbot keeps the first four different talks from the search, so the same talk never gets pasted in twice, and labels each one with the speaker and title. The system prompt explains that the talks came from an automatic search and some might not fit, and tells the model to answer only from the talks, cite a speaker for every point, say so when nothing covers the question, and treat the talks as source material instead of instructions.

When the model kept calling President Christofferson "Elder," I had the code work out each speaker's title from their calling instead of asking the model to. The harder problem was quotes. In the betting talk, Christofferson quotes President Hinckley ("We are against it") and President Oaks ("the taking path of the adversary"), and the model kept crediting both to Christofferson.

| What we tried | Did it credit the quote correctly? |
|---|---|
| The rule in the system prompt | No |
| The same, with reasoning turned on | No |
| A model that costs 10× as much | No, and it was worse |
| Repeating the rule right after the question | Yes |

The rule had been sitting about 7,000 tokens before the question, with four whole talks in between. Moving a copy right next to the question fixed it on the cheaper model, which I didn't expect to matter more than the size of the model.

## 5. Preprocessing vs. tool

In the tool version, the model asks for a search with its own words, my code runs it against Chroma and sends the talks back, and the model can answer or search again up to three times. I ran seven questions through both versions. The tool version found closer matches on all six questions it searched for, because it rewrites the question first. "How can I be saved?" became a search for faith, repentance, baptism, covenants, and enduring to the end. Most answers cost about $0.002 either way, and for a lasagna recipe the tool version skipped the search and refused for a tenth of the cost.

The hardest question was "What were the main themes of this conference?" because the answer is spread across all 38 talks and the search only hands the model a few. Even the tool version, after three searches, was working from about 10 of them. GraphRAG is built for questions like this, since it summarizes the whole collection ahead of time.

When I switched to `gpt-6-luna` and reran the comparison, it cost about half as much and searched more often, even for the lasagna question. It got the betting quote right, but on personal finances it gave President Oaks credit for a point that was Christofferson's own. The quote fix that worked on 5.6-luna went too far on 6-luna, so I'd want to tune it more.

## 6. Checking the answers

Slide 6's RAG triad checks whether the search found relevant talks, whether the answer is supported by them, and whether it actually answers the question. Groundedness was the one I had to check by hand. A citation I doubted, "baptism is the gate" in President Uchtdorf's talk, was correct. One I trusted was wrong: a point about moral agency came from Elder Gong's talk but was credited to Uchtdorf. The answers sounded right almost every time, so the only way to catch mistakes was to check the talks.

Everything in this project cost less than ten cents.

## 7. What I learned

1. **RAG is an open-book test.** The model only knows what's in the prompt, so the search sets a ceiling on the answer.
2. **Search small, read big.** Small chunks find specific ideas, and whole talks give the model the context to answer.
3. **Search always returns something.** Neither filters nor rankings say "nothing relevant," so the system prompt has to handle it.
4. **If code can do it reliably, don't leave it to the model.** Titles were unreliable from the prompt and perfect from code.
5. **Where an instruction sits can matter more than the model.** The quote rule only worked once it was next to the question, and a fix for one model didn't carry over to the next.
6. **Letting the model write its own search helps.** The tool version beat the plain search on every question it searched for.
7. **Citations have to be checked.** I was wrong about which ones were wrong about half the time.
