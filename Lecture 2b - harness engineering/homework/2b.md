# Homework 2b: Harness Engineering

## Summary

For this assignment I built the same app twice from one spec: **Catan Lite**, a hot-seat browser version of *Settlers of Catan*.

- **Build A:** Claude Code with only the prompt `Build the app described in spec.md`.
- **Build B:** Claude Code inside a harness I set up. A planner, a developer, and a reviewer each run as their own subagent, a `/build` workflow ties them together, and hooks enforce the rules I cared about most.

Both builds passed all 20 acceptance scenarios from my spec, so the comparison ended up being about the code, the cost, and what it was like to build. The short version: the harness gave me better-organized code and caught real problems early, but it cost about 3.6× as much and took about 5× as long. With a spec this detailed, the one-shot was already correct.

## 1. The spec

Turn-in: `spec.md`

I picked a cut-down version of Catan because the hard part isn't the UI, it's the data model. Settlements go on hex corners and roads go on edges, and a single corner can be shared by up to three hexes. If an agent stores six corners per hex, several rules quietly break: the distance rule, production from shared corners, and Longest Road. I figured this is where a planning step would matter most.

The spec has:

- an in-scope / out-of-scope table (no development cards, ports, player-to-player trading, or bots)
- the full rules for placement, setup, production, the robber, bank shortages, and Longest Road
- the UI requirements
- a debug mode (forcing dice rolls, giving resources)
- 20 numbered acceptance scenarios, which I used to grade both builds

I intentionally left architecture and data structures out of the spec. I wanted those decisions to be the harness's job.

## 2. Build A: one-shot

Turn-in: `build-a-oneshot/`

I ran the single prompt in a fresh Claude Code session (Opus 5.5), in a folder containing only `spec.md`. After that I didn't send any other messages until it finished.

- 13 minutes, 32 model calls, $3.17 (API-equivalent cost)
- Vite + TypeScript, 41 tests, a clean type check, and every UI requirement from the spec
- It got the key design decision right on its own: corners and edges are stored once, in a single shared graph

Maybe it's just my laziness at play, but it was nice to be able to let the agent loose after developing the spec. That comes at a cost, though: the agent made many decisions for me without consulting me, and it added designs and features I didn't ask for, mainly in the UI.

## 3. Build B: the harness

Turn-in: `build-b-claude/`. `HARNESS.md` in that folder explains every file.

### How I set it up

| Piece | File(s) | What it does |
|---|---|---|
| Project map | `CLAUDE.md` | Loaded into every session. I kept it short: a map of the folder and the hard rules. |
| Planner | `.claude/agents/planner.md` | Has to design the data model first and walk five rules through it. Then it plans the modules, the tests, and 6–10 milestones as checkboxes. It has no Bash tool and doesn't write code. |
| Developer | `.claude/agents/developer.md` | Does exactly one milestone per session, verifies it with the tests and the type check, logs what it did in `progress.md`, and ticks the box. |
| Reviewer | `.claude/agents/reviewer.md` | Reviews the plan, and later the code. It runs the checks itself instead of trusting the developer. It has no Edit tool, and the first line of its review is always a verdict. |
| Workflow | `.claude/skills/build/SKILL.md` + `workflow.py` | Typing `/build` turns the main session into an orchestrator. `workflow.py` reads the handoff files to decide the next step and writes the exact prompt for the subagent. It pauses for me after the plan and after each review. |
| Skills | `.claude/skills/*` | `code-style`, `bottom-up-code`, and `testing` are preloaded for the roles that need them. `project-setup`, `debugging`, and `ui-code` only load when they're relevant. |
| Hooks | `.claude/settings.json`, `.claude/hooks/` | `guard.py` blocks Claude from touching anything outside the folder (so it can't peek at build A) and from editing the spec or the harness. `check.py` won't let a session finish while the tests or the type check are failing. |
| Handoffs | `handoff/` | The only way the roles talk to each other, since subagents don't share any memory. |

### How it connects to the lecture

- **Context isolation:** each role is a subagent with a fresh context window, and only a short summary comes back to the orchestrator.
- **Progressive disclosure:** skill descriptions are always visible, but the full skill only loads when it's needed. `CLAUDE.md` is a map, not an encyclopedia.
- **Determinism over agent decisions:** `workflow.py` decides the step order, which milestone is next, and which review needs fixing, so the model doesn't have to.
- **Agent legibility:** every decision ends up in a file in the repo: plan decisions, deviations from the plan, and review findings.
- **Mechanical enforcement:** the important rules are hooks and tool restrictions, not just requests in a prompt. The planner *can't* run code, the reviewer *can't* edit files, and no session can finish with failing tests.

To keep the comparison fair, I didn't put any Catan-specific hints in the harness. It never says "use a shared corner graph." It only adds process.

### The run

```
plan → plan review (CHANGES REQUIRED) → revised plan → [my checkpoint]
→ M1 … M10 (one subagent each, all passed first try) → code review (APPROVED)
```

- 64 minutes, 235 model calls, $11.42. That includes about 8 minutes of me reading the plan at the checkpoint.
- The plan review caught problems before any code was written:
  - two scenarios were assigned to a milestone that couldn't test them yet, because cities don't exist until the next milestone
  - test helpers were planned before the actions they depend on
  - my spec was ambiguous about Longest Road when the holder is tied but below 5
- The code review checked all 20 scenarios against the actual tests and found one real UI bug: while you're moving the robber, clicking on a building does nothing.

As much as I loved handing the reins to Claude in the previous run, I loved handing them to Claude inside a harness even more. I loved seeing each role report in the Claude session what it had done and implemented. It let me follow what was happening and when, instead of seeing the whole build as one long "Building..." message. Seeing those updates, and seeing that Claude was actually following the harness, gave me more confidence in the product it was building. I had read the plan and judged it well thought out and detailed, so if every subagent did its job, the product would be very functional.

## 4. Comparison

### The apps

Besides each build's own tests, I ran the same independent check script against both builds. It runs each game engine through all 20 scenarios, plus some extra edge cases:

- 1,000 random boards
- no cards created or lost during setup
- a Y-shaped road network and a closed loop of roads
- a third player picking up Longest Road when someone's road gets cut
- winning on another player's turn

| | Build A | Build B |
|---|---|---|
| Independent scenario check | 20/20 | 20/20 |
| Its own tests | 41 | 98 |
| UI requirements | All present | All present, plus 1 minor bug its reviewer found (never fixed) |

Correctness was a tie. My spec, with its acceptance scenarios, basically worked as a harness of its own: it gave the one-shot everything it needed to get the rules right.

Like I experienced with my Kirby games before, the two versions of Catan felt almost the same to play. All of the same features were there, implemented in almost exactly the same ways. The only real difference was the UI, which I'll explain below.

### The surprise: the one-shot looked better

When I played them, build A's UI was much more appealing, which is the same thing I noticed with my Kirby game. Build A added a bunch of things nobody asked for:

- emoji terrain icons (🌲🐑🌾)
- dice faces
- probability dots on the number tokens
- house-shaped settlements and cities
- a 🏆 winner screen

Build B works fine, but it's plain. Looking back at my harness, the reason makes sense: the harness optimized for what it checked, and nothing in it checked how the game looked.

- **Every check was about correctness.** "Done" meant the tests passed, and the reviewer went through the spec section by section. Nothing ever asked whether the game looked good. The plan's whole entry for `style.css` was "Styling | none".
- **My rules for the engine also shaped the UI.** The code-style skill says "don't build more than is needed right now." That's the right call for game logic, but it also made every icon or shadow look like unnecessary scope.
- **The look was split across sessions.** Three different subagents built the UI over milestones M8–M10, and none of them shared memory. A good-looking UI needs one consistent style across the whole page, and no single session owned that. The one-shot designed the whole page at once.
- **The framing changed the agent's job.** "Build the app" makes the agent the product owner. "Complete M9 from plan.md" makes it a contractor working off a checklist, and it delivered the checklist.
- **Nobody could see the result.** My UI skill even says "You can't open a browser," so plain markup was the safe choice.

What I'd change next time:

- put visual goals in the spec
- have the planner write a short visual-design section before the milestones
- only apply the "don't build more than needed" rule to the engine
- add one "visual pass" milestone that owns the whole UI
- let a reviewer take browser screenshots so it can judge the look

### The code

| | Build A | Build B |
|---|---|---|
| Structure | One 557-line `Game` class handles every rule | 13 engine modules, one per rule area; no file over 207 lines |
| State | Methods change the state directly | `applyAction(state, action)` returns a new state, and a failed action leaves the old one untouched |
| Phase rules | Checked separately in each method | One `ALLOWED_ACTIONS` table, checked before anything runs |
| UI | One 407-line template | 7 files, one per area of the screen |
| Tests | 1 per scenario | 1–2 per scenario, testing both what a rule allows and what it rejects |
| Recorded decisions | 4 bullets in the README | 11 numbered decisions in `plan.md`, plus deviations logged every session |

Build B has the better code. Each rule lives in one obvious place, the phase rules are in one table instead of spread around, and because of how state works, a failed action can't change anything. Those choices came straight from the planner role, which had to design the data model before any code was written, and from the code-style skill pushing for small, focused files.

Build A is still clean and well tested, and honestly it's quicker to read in one sitting. Where B should really pay off is when you have to *change* the code. I haven't tested that yet with a real change, like adding ports.

### Cost

| | Build A | Build B |
|---|---|---|
| Time | 13 min | 64 min |
| Cost | $3.17 | $11.42 |

Most of the extra cost comes from context isolation. Every subagent starts from scratch and re-reads `CLAUDE.md`, the skills, the plan, and the code it needs. That added up to about 900k tokens written to cache, compared to 116k for the one-shot. Those fresh, focused contexts are why the harness works so well, and this is what they cost.

### Which did I enjoy more?

The harness. The one-shot was nice because I could just let it go, but it was a black box until it finished, and it made a lot of decisions without me. With the harness I could follow every step, I got to approve the plan before any code was written, and seeing each role report back gave me a lot more confidence in the result. It was slower and more expensive, but I'd take that trade for anything I'd actually have to maintain.

## 5. What I learned

1. **The spec is the first harness.** With 20 acceptance scenarios, the one-shot didn't have much room to be wrong. A better spec might matter more than a better process.
2. **On a project this size, the harness paid off in structure, not correctness.** The difference showed up in how the code was organized and in the problems caught before coding even started.
3. **If a rule matters, enforce it in code.** Telling an agent "don't look at the other build" in a prompt is just a request. In my harness it's a hook that actually blocks the tool call, and I tested it against 21 simulated tool calls before the real run.
4. **A review step needs a follow-up step.** My reviewer found a real UI bug, labeled it "minor," and approved the build anyway. Nothing in my workflow fixes minor findings, so the bug shipped. That's a flaw in my harness design, not in the agent. Next time I'd add a quick fix-up step after approval.
5. **A harness optimizes for what it checks and squeezes out what it doesn't.** Everything in my harness pointed at correctness, so the look of the game got stripped down. It's the same lesson as the unfixed bug: whatever the harness doesn't check or follow up on gets dropped. If something matters, like the game looking good, it needs a place in the spec, a role, and a check.
6. **Context isolation is a trade-off.** It keeps each session focused, but every fresh start costs tokens. Paying 3.6× is worth it for code I'll maintain, not for a throwaway prototype.
7. **Get the numbers from the transcripts.** Every number in this report comes from Claude Code's session logs (`~/.claude/projects/*.jsonl`), not from guesses. Going back through past conversations is how you find out where a harness actually spends its time and money.
