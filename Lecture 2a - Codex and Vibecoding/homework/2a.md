# Homework 2a – Codex and Vibecoding

The main thing I learned from this homework is that I asked for the same game four times and got basically the same game four times from a user perspective. The real differences were underneath, the arcitectuural orject design and code structure.


## Overview

- I vibecoded a pixel-art platformer about our favorite round pink puff-ball hero Kirby. I did so using the same prompt in four different setups. Each one has its own folder:
  1. **`1.1 one-shot v1`** and **`1.2 one shot-v2`**: just the prompt and nothing else. I did two so I could see how much a run changes on its own.
  2. **`2. just agent.md`**: the prompt plus a `CLAUDE.md` I wrote.
  3. **`3. just skills`**: the prompt plus a skill I built with Claude called `grill-me` (like we discussed in calss), which interviews me before building anything.
  4. **`4. agent.md + skills`**: the `CLAUDE.md` and the skill together.
- I used the skill-creator skill to build `grill-me`, tested it against a version of the agent without it, and tried to get its description tuned so it would trigger on its own. I also started a second skill, `game-feel-review`.
- I worked in Claude Code inside VS Code instead of Codex. Every run used **Claude Opus 5.5 on high reasoning** and I left it in **auto mode**, so it never stopped to ask permission.

## 1. The two one-shots

I wanted a prompt that described what the game should do and look like, but said nothing about how the code should be organized or tested. That way the one-shot would show what the agent does by default, and my `CLAUDE.md` later would have something to fix. I started with X as the action key and switched to Enter, because X is hard to reach when you're holding A and D. I also added "work only inside the current directory" to the top so one run wouldn't go peeking at the other.

**What it did well.** Honestly, a lot. Both games ran with no errors and came with a title screen, pause, game over, a win screen, sound effects, and music, all drawn and generated in code with no image files. Both agents also tested themselves without being asked. They wrote a headless Chrome script, took screenshots, looked at them, and fixed what they saw. The first one took 21 minutes and the second took 33. And both of their final messages were honest, saying plainly that they couldn't hear the audio or judge how the movement felt.

**What it did poorly.**
- Each game was one giant file (about 1,650 lines for v1 and 1,890 for v2).
- Nothing useful was left behind. v2 deleted its test folder and v1 left its tests in a temp folder outside my project, so I had nothing to re-run.
- The tests kind of cheated. They teleported Kirby around and flipped flags directly instead of pressing keys, so nobody ever proved the level could actually be beaten. v1 even noticed its win test was "correctly blocked by the goal pedestal since it requires a jump," and then just teleported past it.
- They both got carried away. I asked for two enemy types and each one built four, plus pickups, a high score, and extra keys (X, Z and J) right after I'd told it X was hard to press.
- That "stay inside this directory" line didn't fully work either. v1 still wrote its test harness to a system temp folder.
- They both hit the exact same bug and fixed it the exact same way: the big star you get from swallowing two things spawned inside the floor and popped instantly.

## 2. Writing the CLAUDE.md (run 2)

For run 2 I read both transcripts and wrote a `CLAUDE.md` aimed at the stuff I'd just watched go wrong. (Claude Code reads `CLAUDE.md` instead of `AGENTS.md`, but it's the same idea.) It asked for the game logic to be separate from the drawing code, small files, all the tuning numbers in one place, and tests that actually stay in the project, including a playthrough that can only press keys and no teleporting. It also said to list every extra it adds and to say plainly what it couldn't verify.

It followed the rules well. I got 15 small files and ran the tests myself: all 49 passed, including one where a bot finishes the level with only key presses.

But when I looked at the results, I thought it woudl be drastically different from the one-shots, but they all just seemed really similar. The `CLAUDE.md` changed the code, the tests, and the proof that it works, but not what the player sees. For a game, that was a bit anticlimactic. I don't know why this was. Perhaps because claude is jus so good that its going to do it best even without any sort of frameowrk to work with in auto mode.

## 3. Building a skill with skill-creator

I want to be clear that the skill-creator I used is the one in my Claude environment, not Codex's own `$skill-creator`, so mine might work differently.

I built a skill called **`grill-me`**. When I ask for something new, it looks through the project first and then interviews me one question at a time, with a reason, a recommended answer, and alternatives for each. When it's done it writes a short `DESIGN.md` and waits for my approval before writing any code. I picked this one because I thought it would let me customize the game instead of just taking whatever the model felt like building.

To test it, I gave an agent three casual requests ("i want to add a boss fight at the end of the level") on a copy of the run 2 game, once with the skill and once without. The skill runs passed all 21 of my checks and the no-skill runs passed 17, and they also used slightly fewer tokens and finished faster since they stopped after one question. The single thing the no-skill runs failed every time was asking just one question. They asked six or seven at once.

What surprised me is that the no-skill agents were actually pretty good. I expected them to charge off and start building, but they explored the code, asked sensible questions, and offered defaults. "Go with your defaults" would honestly be fine for plenty of people. I also have to be honest that my test was stacked a little in the skill's favor. I told every agent that no human was present and not to edit anything, which pushed the baseline toward asking questions, and most of my checks were things the skill tells the agent to do anyway.

## 4. Does the skill trigger on cue?

Not very well on its own. I wrote 20 realistic prompts, 10 that should trigger it and 10 near-misses that shouldn't. Then I ran the description tuner. It fired on only about 10% of the ones it should have and never fired on the ones it shouldn't. Five rewrites of the description scored exactly the same, so the tuner kept my original wording and I didn't apply anything. I figured my empty test folder might be the problem, so I ran it again inside a copy of the real game, and got the same result.

Typing `/grill-me` always worked, both times I used it. My guess, and it is only a guess, is that interviewing the user is something the model can do in plain text without ever opening a skill, and the tuner counts a run as "not triggered" if the first thing the agent does isn't reading the skill.

## 5. Runs 3 and 4: using the skill for real

For these two I stopped worrying about one-shots. I typed `/grill-me`, pasted the same prompt, answered the questions, and then told it to build.

The skill did what I wrote. Both runs looked around first, said what they found, and asked one question at a time before writing a `DESIGN.md` and waiting for me. I mostly answered "your rec." What I actually steered was small: I asked for a boss, a spiky enemy you can't inhale, copy abilities, a fire creature to give Kirby the fire power, and unlimited flight. Run 3 took 8 questions and run 4 took 7 plus one more that I'll get to.

Run 4 also used its `CLAUDE.md` in a way I liked. It said its questions "cover only what those rules leave open," skipped everything the file had already settled, and wrote a test that checks the `CLAUDE.md` rules themselves. I re-ran both test suites and everything passes (43 checks for run 3, 62 tests for run 4).

Run 3 took 35 minutes total Run 4 took 54 minutes across two sittings: 8:09 to 8:49 pm, then I ran out of usage and picked it back up at 9:33 the next morning until 9:47.

## 6. Things I didn't expect

- **The model abitrarily made a decision about a feature** In run 4 the agent decided on its own to leave out copy abilities and wrote that into the `DESIGN.md` without marking it as a default. I asked, "in any of the questions, did you mention copy abilities?" and it admitted it hadn't, then asked properly. The approval step only works if I actually read the file, and the skill should treat leaving something out as a decision too.
- **That same floor bug came back for a third time** in run 4, but this time a failing unit test caught it right away instead of the agent finding it by squinting at screenshots.
- **It's expensive.** Run 4 hit my usage limit in the middle of the build, and when I came back the next morning it had to re-cache around 263k tokens.

## Additional exploration

I started a second skill, `game-feel-review`, which measures things like jump height and how long Kirby stays in the air, compares them to target ranges, and then tunes one number at a time. I never got to test the skill itself, but Claude did run its measuring script on a copy of run 2's game, and it found that everything was already inside the target ranges (a jump of about 3.5 tiles high and 0.65 seconds in the air), so there was nothing for it to fix. I think that's because I had Claude build the skill after looking at run 2, and Claude seems to build the basic feel of a game in a similar way no matter what I prompt, unless I get a lot more specific and ask for something different. So I only installed `grill-me` in runs 3 and 4; `game-feel-review` was never part of those runs.

## What I learned & why it matters

- **The prompt decides the game and the instructions decide the engineering.** All four runs felt about the same to play, but they were very different underneath: one big file with no tests versus small files with a bot that proves the level can be finished.
- **A skill only helps if it fires.** The description is basically the routing layer, and mine mostly didn't trigger by itself. Invoking the skill by name always worked though.
- **The approval step is only as good as my attention.** The `DESIGN.md` gate only caught the missing copy ability because I read it carefully.
- **For agent engineering:** this is the same lesson as the last few homeworks. Rules in a prompt are really just requests. The things that matter (a structure test, a playthrough bot, an approval gate) have to be enforced by something that actually runs, and verification I can re-run is worth more than an agent telling me "I checked."
