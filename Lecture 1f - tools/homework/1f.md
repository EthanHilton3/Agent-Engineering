### v1: raw HTML (the expensive mistake)
The OpenAI and Anthropic pages were each somewhere between 139K and 484K characters, and the Star Wars news page was **1,580,871 characters**. And almost none of that was actual text, it was mostly code and styling. So v1 cost **134x** more than not using tools at all, and my transcript file ended up being **2.8 MB** lol. The part I didn't see coming is that tool results stay in the history, so every old page gets sent to the model again with every new question. Which means when I asked for the circumference of the sun (a question that didn't even need a tool) I was still paying for hundreds of thousands of tokens of OpenAI and Anthropic pages I'd fetched earlier.

### v2/v3: strip it down
So I stripped out the scripts, the CSS, and all the HTML tags, but I made sure to keep the links in the form `text (url)`, because without them the model can't follow a link to another page (which ended up mattering a lot for the conference finder). That alone made it **21x cheaper than v1**. Plus 181K of the 208K input tokens in v2 were cached, which is way cheaper than regular input, so that helped too.

## What I learned about tools

### 1. The model never actually runs anything

The model doesn't run any of the tools itself. It just sends back a message that basically says "please call `fetch_url` with this URL," then my code actually runs it and sends the result back with the matching `call_id`. So "tool use" is really just a loop around the API, and all three of my chatbots use the exact same loop. The only thing that changes between them is which tools are in the toolbox.

### 2. Tool results stay in the history (and you pay for them every single call)

This is what made v1 so expensive. Every page the model fetches stays in the conversation history, and the whole history gets sent again on every API call. So a big page doesn't just cost you once, it costs you again on every question after it. Even after stripping the HTML, the George Washington article still cost $0.042 for 5 short questions because it got re-sent with every one of them. So what a tool gives back to the model matters way more than what it downloads.

### 3. Let code do the parts that need to be exact, and the model do the fuzzy parts

Without tools, the model was bad at anything that has to be exact or consistent: a random number, a secret number it's supposed to remember, sticking to one conference. All of those worked once my code was doing them. But the model is really good at the fuzzy stuff, like figuring out that "Quetin" means Quentin L. Cook, matching my paraphrase to the right passage, or deciding which URL to fetch next. So the setup that worked was splitting it up: code for the exact parts, the model for the judgment parts. (Which is basically the guessing game lesson from before, the secret number has to live in code, not in the model's head.)

### 4. Narrow vs. broad tools

`fetch_url` is about as broad as a tool gets. It can fetch anything, which is how the model came up with the wttr.in weather trick on its own, but it's also why it was expensive and kind of unpredictable. `fetch_conference_info` is the opposite. It has no parameters and can only do one thing, so the model can't misuse it and the conference restriction is guaranteed.

### 5. Tools don't fix everything

Even with tools, the model still mixed in stuff from memory (the Star Wars answer called *The Mandalorian & Grogu* "the next film," which wasn't on the page it fetched), it misread data it was literally given (saying Caussé didn't speak when he's right there in the index), and it gave me exact quotes credited to the wrong person (Kimball and McKay). And the same question doesn't always get the same behavior either. The Alabama weather question got "I can't access live weather data" in v1, and then in v2 and v3 it just fetched it, with no code change.

## Why this matters for agent engineering

- **Cost:** When you build a tool you have to think about what it actually gives back to the model, not just whether it works. My fetch tool "worked" in v1, it was just ridiculously expensive.
- **Trust:** An agent with a fetch tool *sounds* like everything it says is sourced, even when part of it came from memory. I only found out about the Kimball and McKay quotes by checking them against the actual talks, so for anything that matters you have to check the claims against what the tool actually returned.
- **Errors are information:** Sending `TOOL_ERROR` back to the model instead of crashing meant it could tell me what went wrong (like the 404 and the PNG), and the chat just kept going instead of dying with a traceback.
