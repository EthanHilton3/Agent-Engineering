# Homework 1g – Agents

## Overview

- For this homework I built my own command-line agent by hand in `agent.py`, starting from the `chat_tools.py` loop we used in class.
- It has five tools I wrote myself (`list_dir`, `read`, `write`, `edit`, and `shell`), and I also gave it OpenAI's built-in `web_search` tool.
- Anything that can change my computer (`write`, `edit`, and `shell`) asks me `Allow? [y/N]` before it runs, and the default answer is no. If I trust what it's doing, I can run it with `--auto` to skip the prompts.
- The zip has `agent.py`, `agent_toolbox.py`, `tools.py`, `usage.py`, my system prompt `agent.md`, two transcripts (`transcript1.md` and `transcript_website.md`), and the spec files the agent wrote in the `website/` folder.

## 1. Building the agent loop

I started with the loop before writing any tools. I based it on the class `chat_tools.py` but changed a few things we talked about in class. My version checks whether the model asked for any tools before it returns an answer, because the class version can return early and skip a tool call if the model also wrote some text. It also stops after 15 turns so it can't loop forever, and if a tool crashes, the error gets sent back to the model as a message instead of taking down the whole program.

- My first version had four bugs that would have crashed it as soon as it ran, and VS Code didn't flag a single one. My favorite was a typo, `"arguements"`, which meant every tool got called with no arguments at all. Lesson learned: no red squiggles does not mean working code.
- While fixing those, I added a fifth bug by calling `.get()` on the objects the API returns, which only works on dictionaries.

## 2. Starting with `list_dir` and `read`

I built the two read-only tools first so the agent could look around my files without being able to break anything.

- My first `list_dir` just returned the raw Python list, so the model got something like `[WindowsPath('agent.py'), ...]`, and it crashed if the folder didn't exist. Now it returns one name per line, with folders listed first and marked with a `/`.
- My own error handling actually hid a bug from me. `read` kept returning "Failed to read file" for every single file, and it turned out I was calling `file.empty()`, which isn't a real method. The `try/except` caught the error and turned it into a polite message, so I only found the problem by calling the tool directly.
- Once these two tools worked, I ran the agent for the first time and asked it how I could improve my `agent_toolbox.py` file. It told me it couldn't see the file and asked me to paste it in, even though the file was in the same folder and it had a `list_dir` tool. It never even tried to look. When I told it to go find the file, it ran `list_dir /` and listed my entire C: drive before finding it. When I asked why it didn't just check the folder in the first place, it said it was "a reasoning failure," but that's a made-up answer, since models can't actually look back at why they did something. I fixed this in section 4.

## 3. `write`, `edit`, and `shell`

- `write` tells the model whether it created a new file or overwrote an existing one, so it knows when it replaced something.
- `edit` only works if the text being replaced shows up exactly once in the file. If it replaced every match instead, it could quietly change the wrong parts of a file and still say it succeeded.
- I had a weird bug where editing one line of a file changed the line endings of the whole file (Windows and Linux use different line endings), so `git diff` showed every line as changed. Now `edit` keeps whatever line endings the file already had.
- `shell` was the hardest tool to get right. Without a timeout, a command that never ends, like starting a web server, froze the agent forever. When I added a 3-second timeout, the command still took 20 seconds, because Windows stopped the shell but not the program the shell had started. I ended up putting the timeout inside the shell command itself so it stops everything, and now 3 seconds actually means about 3 seconds.
- Once the agent could change files and run commands, I added approvals. Before any `write`, `edit`, or `shell` call, it shows me what it wants to do and asks `Allow? [y/N]`. If I say no, the model gets a message saying I rejected it, so it can ask me what I want instead of just failing.

## 4. Fixing the "can't see the file" problem

- The agent always had the right tool to find my file. The real problem was that it didn't know it was running on my computer, so it acted like a normal chatbot.
- I wrote a system prompt, `agent.md`, that tells it things like *"You are not in a chat window"* and *"Never say you can't see or find a file until you have looked."* My code also adds the working folder and today's date to the prompt every time it starts.
- Then I asked the exact same question as before, word for word. This time it ran `list_dir` on its own, read five of my files, and reviewed my actual code. A couple of its suggestions were good, so I added them: `read` now returns 400 lines at a time and tells the model which line to start from next, and it gives a clear message when a file is binary.
- Later I had a bigger model (`gpt-5.6-sol` with medium reasoning) review the toolbox again, which is the first conversation in `transcript1.md`. It found a real gap: when `write` overwrites a file, my approval prompt only shows the new content, so I can't see what I'd be losing. But it also suggested giving my tool parameters default values, which would break the strict schema my tools use. That was the third time a model suggested that. It also said the tools it had were "almost identical to yours," not realizing it was reviewing its own tools lol.
- I also added the transcript feature from my 1f homework, so every chat gets saved to a Markdown file along with each tool call and what it returned.

## 5. Adding `web_search`

- `web_search` is one of OpenAI's hosted tools, which means OpenAI does the actual searching during the API call. To turn it on, I only had to add it to the list of tools I send with each request.
- My agent loop didn't need any changes, because the loop only runs the tools I wrote, and the searches come back already finished. `agent_toolbox.py` didn't change either, since a hosted tool doesn't have any Python code on my end.
- I added a few things so I could see what it was doing. It prints each search it makes, lists the sources it cited under its answer, and lets me choose how much search text the model reads with `--search-context-size`.
- The cost surprised me the most. One question cost about $0.002 in tokens, but the search itself costs $0.01, so the search was about five times more than the tokens. 

## 6. Using it to plan a website

For the "use it instead of Codex" part, I had it help me plan a website I actually want to build: a personal media tracker where you log every movie or episode you watch as an "experience" and can set goals like watching all of *Avatar: The Last Airbender*.

- When I asked if there was an API for movie and TV data, it searched the official TMDB and IMDb developer docs instead of random sites, and then recommended TMDB with eight sources to back it up.
- It listened to me. When I told it to explain its plan before writing anything, it didn't touch the file. When it disagreed with one of my ideas (I wanted "dropped" to be a type of "in progress," and it pointed out that a dropped goal isn't really in progress), it explained why before changing anything.
- The final spec ended up being 610 lines, so this was the first time I saw the 400-line limit on `read` actually get used. It read the file in two parts.
- It wasn't perfect. Some of its answers were around 400 lines long even though my prompt tells it to be concise, the spec almost doubled in size after I asked for it to be "not too long," and at one point it said it had "verified" six edits after only re-reading two of them.
- Compared to Codex, mine is a lot less polished. There's no undo, no nice diffs, and I can only type one line at a time. But I can see every tool call it makes, I approve everything, and I know exactly how much each session costs.

## What I learned & why it matters

- The agent loop itself was the easy part. Most of my time went into the tools and all of their edge cases, like timeouts, line endings, and weird files.
- Giving the model the right context mattered more than giving it more tools. My agent already had everything it needed to find my file, it just didn't know where it was until I told it.
- Rules in a prompt are only requests. If I really don't want the agent to do something, the code has to enforce it with things like approvals, timeouts, and output limits. That matters a lot once an agent can run real commands on your computer.
- Whether a tool runs on OpenAI's side or on mine decides how much work my loop has to do. My own tools need my loop to run them, but `web_search` just runs.
- Models are good at reviewing code in general, but they don't always check their ideas against how your code actually works, so I still have to decide which suggestions make sense.
